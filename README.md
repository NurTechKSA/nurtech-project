# TaskManager

Учебный таск-менеджер в духе Jira: проекты, доски с колонками, карточки задач с комментариями, связями и учётом времени. Фронтенд — Angular 21, Taiga UI 5 и `@ngrx/signals`; бэкенд уже готов и работает на стенде.

## С чего начать

1. **Посмотрите на продукт.** Откройте [стенд](https://tasks.45.77.66.108.sslip.io) — там то, что уже сделано. Каким продукт должен стать, показывают [макеты](https://github.com/NurTechKSA/nurtech-project/tree/docs/mvp/docs-short/wireframes): доска, карточка задачи, создание задачи, вход и профиль, верхняя панель.
2. **Узнайте границы MVP.** [01-scope](https://github.com/NurTechKSA/nurtech-project/blob/docs/mvp/docs-short/01-scope.md) — что делаем сейчас, что отложено, какие есть роли и адреса страниц. Остальные документы читайте, когда возьмёте задачу по ним.
3. **Запустите проект локально** — раздел [Запуск](#запуск) ниже. Войти можно тестовым пользователем, пароль даст ментор.
4. **Осмотрите код.** Раздел [Архитектура](#архитектура) объясняет, где что лежит; готовые примеры — вход, верхняя панель, права в `src/app/core`.
5. **Возьмите задачу** из бэклога Taiga, создайте ветку и откройте PR — как в разделе [Ветки и PR](#ветки-и-pr). Перед первым PR прочитайте [Код-стайл и проверки](#код-стайл-и-проверки).

## Запуск

Нужны Node.js `^20.19 || ^22.12 || >=24` и npm `>=11`.

```bash
npm ci
npm start
```

Приложение откроется на `http://localhost:4200`. Запросы на `/api` dev-сервер проксирует на стенд — адрес задан в `proxy.conf.json`.

Сессия хранится в httpOnly-cookie, поэтому фронт и `/api` всегда открываются с одного адреса: в разработке это делает прокси, на проде — веб-сервер.

| Команда                                   | Что делает                                                        |
| ----------------------------------------- | ----------------------------------------------------------------- |
| `npm start`                               | dev-сервер с прокси                                               |
| `npm run build`                           | продакшен-сборка                                                  |
| `npm run lint` / `lint:fix`               | ESLint для `.ts` и шаблонов                                       |
| `npm run lint:styles` / `lint:styles:fix` | stylelint для `.scss`, порядок свойств исправляется автоматически |
| `npm run format` / `format:check`         | Prettier                                                          |
| `npm run check`                           | все проверки CI, кроме сборки                                     |

## Код-стайл и проверки

Форматирование не обсуждаем — его делает Prettier. Правила кода проверяют ESLint (`.ts` и шаблоны) и stylelint (`.scss`). В VS Code поставьте рекомендованные расширения из `.vscode/extensions.json`: ошибки будут видны сразу, а форматирование — по сохранению.

Что проверяет линтер и на чём чаще всего спотыкаются:

- Имена файлов `kebab-case.<тип>.ts`: `task-card.component.ts`, `board.store.ts`.
- Компоненты с `OnPush`, на сигналах; `output()` вместо `@Output()`.
- Порядок в классе: приватные поля → публичные → конструктор → методы.
- Булевы переменные с префиксом `is`, `has`, `can` …; у интерфейсов нет префикса `I`.
- `Observable` — с суффиксом `$`, `Subject` — с `$$`. Обработчики в `subscribe()` не передаём — логика уходит в операторы (`tap`, `switchMap` …).

Чего линтер не ловит, но на ревью попросят:

- Импорты из `core` и `shared` — через `@core/…` и `@shared/…`, внутри домена — относительные.
- Один файл — одна экспортируемая сущность. Тип или константа, нужные только одному файлу, остаются в нём без экспорта.
- В шаблоне читаем сигналы, а не вызываем методы и геттеры: вычисления — в `computed`, форматирование значений — пайпом.
- В шаблоне нет логики: события идут в обработчики `onXxx()` — `(click)="onSaveClick()"`, а не `(click)="isOpen.set(true)"`.
- Типы полей — из модели контракта, а не примитивом: `id: Task['id']`, `input.required<Task['priority']>()`.
- Имена функций — с глагола, без самодельных сокращений.
- Комментарии — только к неочевидному; JSDoc — для действительно ценного описания.
- У компонентов страниц, диалоговых окон,- без `selector`-а компонента.
- Сначала ищем готовый компонент Taiga UI, свою вёрстку пишем, только если готового нет: пустые экраны и ошибки — `tui-block-status`, карточки — `tuiCardLarge`, и так далее.
- Размер и положение компонента задаёт родитель, сам компонент оформляет только своё содержимое.

Проверки работают в три слоя:

1. **Редактор** подсвечивает ошибки, пока пишете код.
2. **При пуше** husky запускает `npm run check` и не пускает код с ошибками. Упал — запустите `npm run *:fix`, остальное поправьте руками.
3. **CI** на каждый PR повторяет те же проверки и добавляет сборку. PR с красным CI на ревью не берётся.

## Отладка

Состояние сторов и их экшены видны в расширении браузера [Redux DevTools](https://github.com/reduxjs/redux-devtools).

## Архитектура

```
core/       то, без чего приложение не стартует: аутентификация, layout, права, текущий пользователь и проект
shared/     переиспользуемый код без доменной логики
<домен>/    экраны и логика одной предметной области: board/, task/, profile/ …
```

- Внутри домена файлы раскладываются по типу сущности. Как именно — видно по `core`.
- `shared` ни от чего не зависит, `core` — только от `shared`, домены — от `core` и `shared`. Страницы и компоненты чужого домена не импортируем.
- Состояние живёт в сторах: общее для приложения — в глобальных, состояние экрана — в сторе страницы. В сторе только состояние и работа с ним; навигация, диалоги и прочий UI остаются в компонентах или сервисах.
- Сторы зависят друг от друга в одну сторону, без циклов: `ProjectStore` вызывает `PermissionStore`, но не наоборот.
- Guard только проверяет доступ и ждёт данные, но не меняет состояние под адрес: переход могут отменить, и в сторе останется чужое значение. Состояние под адрес выставляет компонент маршрута.
- Сетевые ошибки (401, 403, 409, 5xx, нет сети) обрабатывают перехватчики. Страница отвечает только за ошибки, которые касаются её самой: 404, ошибки полей формы.

## Ветки и PR

- Ветка от свежего `main`: `feat/board-columns`, `fix/card-dialog-close`. PR — в `main`, после мержа стенд сам забирает изменения.
- Одна задача — один **или несколько** PR. Чем меньше строк, тем быстрее ревью. Лучше быстро загрузить хоть что-то, чем долго не сделать ничего.
- Не правим «заодно» то, что к задаче не относится: рефакторинг и чужой код — отдельным PR.
- Сначала перекрёстное ревью (cross-review), потом финальное.

### Коммиты и PR

Ориентир — история `main`: размер, детализация и формулировки там такие, какие ждём от вас.

- Формат — `тип: Что сделано`, одной строкой, по-русски, с заглавной буквы, без точки в конце. Формулировка — результат, а не процесс: «Добавлен», «Исправлено», «Вынесен», а не «добавляю» или «фикс».

  ```
  feat: Добавлен authGuard и возврат на исходный адрес после входа
  feat: Добавлен перехват 401 со сбросом сессии и переходом на вход
  fix: Каркас приведён к контракту
  ```

- Тип совпадает с префиксом ветки:

  | Тип        | Когда                                                 |
  | ---------- | ----------------------------------------------------- |
  | `feat`     | новая возможность для пользователя                    |
  | `fix`      | исправление ошибки                                    |
  | `refactor` | переработка без изменения поведения                   |
  | `style`    | стили, линтеры и форматирование                       |
  | `chore`    | инфраструктура: зависимости, утилиты, хуки, настройки |
  | `docs`     | документация                                          |

- Размер PR — обычно 50–300 строк и до десятка файлов. Больше — повод разбить задачу.
- Заголовок PR совпадает с сообщением коммита. В описании — ссылка на задачу, что сделано (коротко, списком), как проверить и скриншот или видео, если меняется интерфейс.
- Коммитов в PR может быть несколько, но каждый осмысленный и в том же формате: «правки», «wip» и «fix review» не пишем.
