# План MVP: этапы, часы, задачи

Часы — ученика (не опытного разработчика). Ёмкость: 13 учеников × 7 ч в неделю, ≈ 20% уходит на онбординг и ревью, план берётся с запасом 15%. Процесс: ветки `dev` и `main`, перекрёстное ревью, одна задача — один PR, задача ≤ 6 ч; оформление задач — раздел 2, DoD — раздел 8. Каркас ментора и бэкенд готовы: все задачи сразу делаются на реальном API стенда.

## 1. Ёмкость и итог
| Величина | Расчёт | Часы |
|---|---|---|
| Чистая ёмкость в неделю | 13 × 7 × 0,8 | 72,8 |
| План в неделю (запас 15%) | 72,8 × 0,85 | ≈ 62 |
| Работа учеников | раздел 4, без «на потом» | 268 |

≈ 268 ч — это ≈ 4,3 недели плановой ёмкости, ориентир — **5–6 недель** (зависимости растягивают хвост); остальное время — резерв (раздел 6). Приглашение (9 ч) в расчёт не входит: оно в беклоге «на потом».

## 2. Как устроены задачи
**Два уровня.** В Taiga по колонкам Kanban двигается только User story, поэтому:
- **Фича** («Доска задач», «Поля карточки», «Комментарии») — **Epic** Taiga: контейнер, показывает прогресс по своим задачам.
- **Задача** — **User story** Taiga: одну задачу берёт один ученик, одна задача — один PR, ≤ 6 ч (чаще 2–4 ч). Подзадачи Taiga (Task) не используются.
- **Этап** (Э0–Э7) — не уровень, а тег: шаг поставки, после которого продуктом можно пользоваться больше. Этапы задают порядок карточек в Backlog.

**Вводная задача фичи.** Каждая большая фича начинается с одной вводной задачи: она создаёт место фичи в архитектуре — домен или папку в нём, интерфейсы по контракту, сервис запросов, стор и заготовку (страницу, диалог, панель или вкладку с местами под блоки), уже показывающую реальные данные. Остальные задачи фичи ждут только её и делаются **независимо друг от друга**: каждая добавляет свой блок в своё место.

**Где что лежит** (README, «Архитектура»):
| Домен | Что | Вводная задача |
|---|---|---|
| `shared/` | аватар, окна подтверждения, копирование ссылки, форматы времени и дат, тексты ошибок | не нужна: каждая задача SHR — отдельный файл |
| `task/` | типы задачи, бейджи приоритета и типа, статус, ключ; карточка, поля, создание, описание, подзадачи, связи, комментарии, время, история | TSK-1 (домен и типы), затем вводные фич: CRD-1, CRT-1, FLD-1, LNK-1, CMT-1, WLG-1, HST-1 |
| `board/` | доска, колонки, карточка на доске, перенос, фильтры, автообновление | BRD-1, затем FLT-1 и MOV-1 |
| `profile/` | профиль | PRF-1 |

**Слои.** Внутри фичи работа идёт от данных к поведению: **данные** (интерфейсы, сервис, стор — во вводной задаче) → **вёрстка на реальных данных** → **логика** (адрес, действия, сохранение, ошибки, права). Если блок небольшой, вёрстка и логика — одна задача (каждое поле карточки, каждый фильтр); если большой — отдельные (доска, перенос).

**Связность.** У каждой задачи в разделе 4 указано, чего она ждёт (колонка «Ждёт»). В Taiga это флаг «Заблокирована» и строки «Ждёт» и «Блокирует» в описании. Правила:
- задача ждёт **вводную задачу своей фичи** и только то, без чего её не сделать или не проверить: компоненты, которые она показывает, и соседнюю логику (открытие карточки ждёт адрес доски, перенос в Blocked — окно причины);
- общее делается раньше потребителей и один раз: компоненты Э0 — раньше доски и карточки, окно причины — в поле «Статус», поля карточки — раньше полей диалога создания, просмотр markdown — раньше комментариев;
- задачи одной фичи друг друга не ждут, если работают в разных местах заготовки; если правят один файл — выстроены цепочкой;
- вводная задача данных почти ничего не ждёт: её можно взять раньше своего этапа.

**Оформление в Taiga.** Название: `Фича: что сделать`, например «Доска: вёрстка карточки на доске». Описание:
```text
Контекст: зачем задача и что получится в продукте
Документ: docs-short/NN-….md §X, сценарии приёмки; макет
Swagger: http://localhost:4200/api/docs/#/Tasks/getTaskByKey (или весь Swagger и список нужных данных)
Ждёт: #… · Блокирует: #…
Что важно: детали, ради которых задача существует, и ловушки
Не входит: что делается в соседних задачах
Приёмка: пункты из раздела «Приёмка» документа (Дано / Действие / Ожидаю)
DoD: docs-short/02-plan.md §8
```
Подсказок «какой файл открыть» нет. Если ручка одна и очевидна — ссылка прямо на неё в Swagger; если нужно несколько — словами, какие данные понадобятся, и ссылка на весь Swagger. Теги: этап (`Э1`), слой (`данные`, `вёрстка`, `логика`), сложность (`easy`, `medium`, `hard`).

## 3. Планирование и статусы
Жёсткого деления на недели нет. Раз в неделю ментор проводит планирование: смотрит Backlog и по загрузке команды переносит задачи в Plan. Что не успели, остаётся в Plan или Backlog и берётся на следующем планировании.

Статусы Kanban повторяют шаблон проекта `dev` нашего продукта ([backend/01](backend/01-auth-projects.md) §5), чтобы процесс команды был примером того, что она разрабатывает:

| Статус | Что значит |
|---|---|
| Backlog | Все задачи MVP в порядке этапов |
| PBR | Ментор уточняет задачу: описание, зависимости, оценка |
| Plan | Взята на эту неделю на планировании |
| To do | Всё, чего ждёт задача, в Done — можно брать |
| In progress | Взята учеником, ветка создана |
| In review | Открыт PR: перекрёстное ревью и ревью ментора |
| Done | PR смерджен в `dev` |
| Blocked | Работа встала (вопрос к ментору или бэкендеру); причина — в комментарии |
| Cancelled | Задача больше не нужна |

**Как планировать.**
- В Plan берутся задачи, у которых всё, чего они ждут, в Done. Можно брать и задачу, которая ждёт короткую (≤ 3 ч) задачу, взятую в ту же неделю: та будет готова в первые дни.
- Вводные задачи фич (BRD-1, CRD-1, FLD-1, FLT-1, …) — в начало недели и сильным ученикам: от них зависит, сколько задач откроется дальше.
- Пока ученик ждёт ревью, он берёт вводную задачу следующей фичи или задачу Э0.

Так выглядит беклог при плане ≈ 62 ч в неделю (проверено моделью по колонке «Ждёт»):
| Неделя | Задач | Что открывается |
|---|---|---|
| 1 | ≈ 20 | Э0 целиком, вводные доски и карточки |
| 2 | ≈ 15 | вёрстка доски, адрес доски, шапка и страница карточки, вводные создания, полей, переноса; описание, подзадачи, связи |
| 3 | ≈ 14 | диалог карточки, все поля, перетаскивание, вводная фильтров, сохранение описания, ссылки, вводная комментариев |
| 4 | ≈ 17 | открытие с доски, отправка создания, фильтры, порядок переноса, комментарии, время, история |
| 5 | ≈ 7 | ошибки переноса, автообновление, Subtask, правка комментариев и времени |
| 6+ | — | стабилизация и резерв |

**Контрольные точки** (ориентир; при 13 учениках по 7 ч ≈ 62 ч плана в неделю):
- **КТ1 (≈ неделя 3):** Э0–Э2 — доска на реальных данных, задачу можно создать и открыть в диалоге и на странице.
- **КТ2 (≈ неделя 4):** Э3–Э5 — правка полей, перенос, фильтры, описание, подзадачи, связи.
- **КТ3 (≈ неделя 6):** Э6–Э7 — комментарии, время, история, стабилизация, временный код удалён, релиз MVP в `main`.

## 7. Риски
| Риск | Мера |
|---|---|
| Ментор не успевает с ревью | Перекрёстное ревью учеников, маленькие PR (слои API / UI / логика), линтер в CI |
| Задачи ждут друг друга | Колонка «Ждёт» и флаг «Заблокирована» в Taiga; длинные цепочки берутся первыми; пока ждут, ученики берут данные следующих фич и задачи Э0 |
| Конфликты слияния в карточке и на доске | Компоненты по файлам; задачи, правящие один файл, выстроены цепочкой |
| Общие тестовые пользователи: кто-то сменил пароль или имя | Правило «проверили — верните» (README); при поломке бэкендер сбрасывает сид |
| Оценки не откалиброваны | Пересчёт выработки на КТ1, резерв после КТ3 |

## 8. DoD (готово, когда)
- [ ] Все пункты приёмки задачи пройдены вручную на `DEMO` и записаны в PR («Дано / Действие / Ожидаю → результат»).
- [ ] Если задача касается действий — под `eva_viewer` недоступное скрыто.
- [ ] Состояния загрузки, пусто и ошибки сделаны или явно отнесены к другой задаче.
- [ ] Тексты и термины — по [03](03-ui-rules.md).
- [ ] `npm run check` и сборка проходят, CI зелёный.
- [ ] PR в `dev`: одна задача — один PR, перекрёстное ревью пройдено, замечания закрыты.
- [ ] В Taiga: статус обновлён, ссылка на PR, фактические часы — комментарием.
