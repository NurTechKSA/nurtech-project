# План MVP: этапы, часы, задачи

Часы — ученика (не опытного разработчика). Ёмкость: 13 учеников × 7 ч в неделю, ≈ 20% уходит на онбординг и ревью, план берётся с запасом 15%. Процесс (ветки `dev` и `main`, перекрёстное ревью, PR на одну задачу, задача ≤ 6 ч) — как в `docs/01-scope.md`, «Процесс»; шаблон карточки задачи в Taiga и DoD — `docs/15-backlog.md`. Каркас ментора и бэкенд готовы: все задачи сразу делаются на реальном API стенда.

## 1. Ёмкость и итог
| Величина | Расчёт | Часы |
|---|---|---|
| Чистая ёмкость в неделю | 13 × 7 × 0,8 | 72,8 |
| План в неделю (запас 15%) | 72,8 × 0,85 | ≈ 62 |
| Работа учеников | раздел 4, без E6 | 275 |

≈ 275 ч — это ≈ 4,5 недели плановой ёмкости, ориентир — **5 недель**; остальное время — резерв (раздел 6). Приглашение (9 ч) в расчёт не входит: оно в беклоге «на потом» (E6).

## 2. Как устроены задачи в Taiga
- **Эпик** — раздел продукта (E0–E6 ниже). **История** (user story) — фича внутри эпика, например «Страница доски». **Задача** (task) — то, что берёт один ученик и двигает по доске спринта; одна задача — один PR.
- Задача ≤ 6 ч, чаще 2–4 ч. В описании задачи — ссылка на раздел документа и сценарии приёмки (колонка «Источник»).
- **Начало — знакомство с проектом (E0).** Небольшие отдельные задачи по 1–3 ч в разных частях каркаса: каждая учит одной важной детали (права, адрес, формат, доступность). Большие разделы берутся, когда команда освоилась.
- **Большая фича делится на слои**, чтобы PR оставались маленькими:
  1. **API и стор** — интерфейсы ответов по OpenAPI, `Api*Service`, стор со статусом загрузки (`withLoadingStatus`) и методами. Без UI.
  2. **UI** — компоненты без запросов: данные через `input()`, события через `output()`, все состояния с макета. Проверяется на данных, переданных из родителя.
  3. **Логика** — страница соединяет стор и UI: маршрут, параметры адреса, обработка событий, ошибки, права.

  «API и стор» и «UI» идут параллельно у двух учеников, «Логика» — после обоих. Если логика большая, она делится на несколько задач.
- Названия задач: `<История>: <слой или часть>`, например «Страница доски: API и стор».

## 3. Планирование и статусы
Жёсткого деления на недели нет. Раз в неделю ментор проводит планирование: смотрит беклог и по загрузке команды переносит задачи в «План». Что не успели, остаётся в беклоге или в «Плане» и берётся на следующем планировании.

| Статус Taiga | Что значит |
|---|---|
| Backlog | Все задачи MVP в порядке приоритета (порядок эпиков и историй ниже) |
| Plan | Взяты на эту неделю на планировании |
| Todo | Готовы к работе: зависимости смерджены, можно брать |
| In progress | В работе у ученика, ветка создана |
| Review | Открыт PR, идёт перекрёстное ревью и ревью ментора |
| Done | PR смерджен в `dev` |

Зависимости между задачами — связь «Блокирует» (как в нашем продукте): «Логика» заблокирована своими «API и стор» и «UI». Задачу из «Плана» переносят в «Todo», когда блокирующие задачи в Done.

Порядок работ (ориентир): E0 и профиль → API и UI доски и карточки → логика доски, фильтры, оболочки и поля карточки → перенос, описание, подзадачи → связи, комментарии, время, история → диалог создания → стабилизация.

- **КТ1 (≈ неделя 2):** доска с колонками, карточками и фильтрами на реальных данных; главная ведёт на доску; диалог и страница карточки открываются со шапкой.
- **КТ2 (≈ неделя 4):** перенос карточек с порядком и причиной; карточка полностью (поля, описание, подзадачи, связи, ссылки, комментарии, время, история).
- **КТ3 (≈ неделя 5):** диалог создания, стабилизация, временный код удалён, релиз MVP в `main`.

## 7. Риски
| Риск | Мера |
|---|---|
| Ментор не успевает с ревью | Перекрёстное ревью учеников, маленькие PR (слои API / UI / логика), линтер в CI |
